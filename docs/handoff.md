## 今の結論

Windows 11 + わんコメ 9.1.6 + OBS 32.1.2 の実機で、次が動くことを確認した。

- プラグインがわんコメに認識され、REST が通る

## 実機で分かったわんコメの挙動

ここが一番重要。**公式ドキュメントに書かれておらず、実機のログを取って初めて分かったもの**を並べる。推測で書いたコードはここで2回間違えた（後述）。

### 1. `subscribe('comments')` のペイロードは配列ではない

プラグインには次の形で届く。SDK の `PublishActions` に書かれた WebSocket API の形（`Comment[]`）とは**違う**。

```js
subscribe('comments', { comments: [ ... ], userNameMap: {}, options: {} })
```

実データの例（コメントテスターから1件）:

```json
{
  "id": "COMMENT_TESTER",
  "service": "youtube",
  "name": "CommentTester",
  "data": {
    "id": "yt-1793588068532",
    "liveId": "youtube-test",
    "userId": "テストユーザー",
    "name": "テストユーザー",
    "isOwner": false, "isMember": false, "hasGift": false,
    "comment": "そうだよねー",
    "timestamp": "2026-11-02T02:54:28.532Z"
  },
  "meta": {}
}
```

`plugin.js` の `commentsOf()` が、オブジェクト形と配列形の両方を受けるようにしてある。

### 2. `comment.id` は「枠の ID」であって、コメントの ID ではない

上の例で最上位の `id` が `"COMMENT_TESTER"` になっている通り、**同じ配信枠のコメントは全件が同じ値**になる。コメントごとに一意なのは `data.id` のほう。

SDK の型定義（`Comment.d.ts` の `Reaction.id` の説明）にこう書かれている：

> このリアクションが届いた枠の ID（`Service.id`。コメントの `comment.id` と同じ値）

重複排除のキーには **`data.id` を使うこと**。`comment.id` を使うと2件目以降が全部「処理済み」として捨てられる。

### 3. 再配送は `meta.isUpdate` で判別する

SDK の `BaseCommentMeta.isUpdate` の説明に、こう明記されている：

> プラグインやテンプレートで件数を数える場合は、このフラグが立った配送を除外すること。

再接続時のバックログ取り直し、連投による個数更新、金額の後追い確定などで立つ。`ingestComment()` の冒頭で弾いている。

### 4. REST のレスポンスは二重に包まれ、HTTP ステータスは常に 200

プラグインが返した `{ code, response }` が、そのまま JSON として返ってくる。

```json
{"code":200,"response":"{\"schema\":1,...}"}
```

プラグイン側が 400 を返しても **HTTP は 200** のままなので、`res.ok` は当てにならない。`common.js` の `readJson()` が包装を剥がし、中身の `error` を見てエラー判定している。

プラグインが未登録・無効のときは、わんコメ本体がこう返す（＝エンドポイント自体は生きている）：

```json
{"statusCode":400,"error":"Bad Request","message":"Notfound plugin (fc-counter.local)"}
```

### 5. デバッグは `plugin.log` を見る

プラグイン内で `console.log()` を呼ぶと `%APPDATA%\onecomme\logs\plugin.log` に出る。`api.log`（`PluginLogger`）も同じ場所へ出る。

**届いたイベントの中身が分からないときは、`subscribe` の先頭で `JSON.stringify(args)` を吐かせるのが最短**。今回の2つのバグはこれで特定した。仕込んだら、わんコメのプラグインウィンドウで「再読み込み」すること（再読み込みしないと反映されない）。

### 6. 検証の主力は「コメントテスター」

わんコメ本体のダミーコメンター機能。**配信も課金もせずに本物のデータ形式が流せる**ので、これが検証の中心になる。

- サービスを選ぶと、そのプラットフォームの本物の形式で届く
- ギフト/スパチャを「あり」にすると、ギフトタイプ（スーパーチャット、メンバーシップギフト、ジュエル等）と**金額**を指定して送れる
- 繰り返し間隔（ms）を指定して連投もできる

ただし **`meta`（同接・高評価）は流れない**。そこだけは配信枠の接続が要る。

### 7. OBS の CEF は 127（Chromium 127 相当）だった

OBS 32.1.2 のログに `[obs-browser]: CEF Version 127.0.6533.120` と出ていた。`color-mix()` も CSS の `translate` プロパティも使える世代。ただし**相手の OBS が古い可能性は残る**ので、今の保守的な書き方（新しめの CSS を避ける）は維持している。OBS のバージョンは `%APPDATA%\obs-studio\logs\` の最新ログで確認できる。

## 2026-11-02 に直したバグと、その経緯

**最初の実装は Mac 上で、わんコメの代わりに `dev/server.js` を使って行った。** テストは9件とも通っていたが、Windows 実機に載せたらコメントが1件も数えられなかった。

原因は2つで、どちらも**例外を出さずに黙って0のまま**になる種類だった。

1. `subscribe('comments')` の中身を配列だと想定していた。実際は `{comments, ...}` のオブジェクト。`Array.isArray()` の判定に落ちて、毎回空配列として処理していた。
2. 重複排除のキーに `comment.id` を使っていた。これは枠の ID なので、同じ配信のコメントが全部同じキーになり、1件目以降が捨てられる。

**テストが9件とも通っていたのは、テスト自体が同じ間違った想定を写していたから**だった。テストのヘルパーを実データの形（枠 ID は共通・`data.id` が一意・ペイロードは `{comments}` 包み）に直したところ、修正前のコードでは既存9件のうち5件が落ちた。回帰テストを3件足して、現在12件。

**教訓**：自分で作った偽データで通したテストは、自己採点でしかない。わんコメのイベントの形は SDK の型定義（`npm pack @onecomme.com/onesdk` で取れる `dist/types/`）を一次情報にし、それでも分からない部分は `plugin.log` に実データを吐かせて確かめること。

## 次にやること

### 1. `meta`（同接・高評価）の検証 ← 最優先

残った唯一の穴で、**上と同じ「黙って0のまま」になる構造**を持っている。`ingestMeta()` は次を想定しているが、実データで確かめていない。

- ペイロードの形が `{ type, service, data }` であること
- 同接が `data.viewer`（`number | string` の両方ありうる）に入ること
- 高評価が `data.totalLikeCount`（無ければ `data.upVote`）に入ること

欄の名前は SDK の `Service.d.ts` の `ServiceMeta` で確認済みだが、**プラグインに渡される際の包み方が `comments` と同様に違う可能性がある**。

手順：

1. わんコメに適当な YouTube のライブ配信の URL を枠登録する（自分で配信しなくてよい。他人のライブでよい）
2. `subscribe` の `type === 'meta'` の枝で `JSON.stringify(args[0])` を `console.log` する
3. `plugin.log` に出た中身と `ingestMeta()` の想定を突き合わせる
4. ずれていたら直し、テストを足して `npm test` を通す

### 2. メンバー加入・ギフトの確認

コメントテスターのギフトタイプで `Membership Gift` 等を送り、メンバー加入として数えられるか、かつコメント件数には**含まれない**ことを確認する。`giftType` の取りうる値は SDK の `YouTube.d.ts` に `'superchat' | 'supersticker' | 'sponsorgift' | 'giftreceived' | 'milestonechat' | 'subscribe' | 'jewel'` と定義されている。

### 3. 本番配信での通し運用

実際の配信で一度通すまでは「動いた」と言い切らない。

## 設計で決めたことと理由

| 決めたこと | 理由 |
|---|---|
| わんコメの「プラグイン」に集計と保存をさせ、テンプレートは REST で読む | 表示画面（OBS ブラウザソース）と操作画面（OBS ドック）の間で状態を共有する手段が確かめられていなかった。プラグインを唯一の状態の持ち主にすれば共有の問題が消え、表示画面を2枚開いても二重に数えない |
| テンプレートは OneSDK を使わず `fetch` でポーリングする | 集計はプラグインが済ませているため、テンプレートはコメントを受け取る必要がない |
| 目標を越えても周回させず、100% を超えて表示し続ける（例: 120%） | 主旨が「どれだけ達成したか」で、周回より達成率のほうが直接伝わる |
| 達成演出は項目ごとに1回だけ。目標や値を手で書き換えたときは演出を出さない | 同接のように上下する値が目標を何度もまたいでも、演出が繰り返し出ないようにするため |
| スパチャは円建てだけを合計する | 為替換算を持ち込まないため。外貨の扱いは必要になってから決める |
| スパチャはコメントとしても数え、メンバー加入とギフトの通知は数えない | 本文付きのものだけを「コメント」と見なすため |
| 見た目は「丸い器に水がたまる」形にした | 達成率が直感的に分かるため。素材は使わず、CSS と SVG で描いた |

## 経緯と前提

- **主旨**: 配信中に、コメント数や視聴者数を、決めた目標に対する達成度としてリアルタイムに可視化する。
- **参考にしたもの**: 同種の市販ツールを見て「器に水がたまる」という方向性だけを採った。**機能・見た目・素材はいずれも複製していない。** 表示は CSS と SVG で一から描いてある。
- **コメントの取得経路**: わんコメ経由。API キーが要らず、実装が一番簡単だから。
- **見た目と技術スタック**: 実装者に任されていた。条件は「簡単に実装できる感じで」。ビルド工程なしの素の HTML/CSS/JS。
